把数学建模备赛变成一个可复用工程

这段时间我把数学建模国赛的准备工作整理成了一个仓库：math-2026。

它一开始只是一个备赛资料夹：代码模板、论文模板、往年赛题、一些教程链接。整理到现在，它慢慢变成了一个更像“作战工作台”的东西：Windows 负责跑模型，Mac 负责写论文；本地沉淀完整工程；优秀论文不只是收藏，而是拆成建模、画图、摘要和验证方法。

这篇文章算是一次阶段性复盘：仓库现在有什么、我从优秀工程里学到了什么、以及赛时真正值得守住的几条方法。

这个仓库现在解决什么问题

数学建模备赛很容易陷入一种状态：资料很多，但真正比赛时不知道该从哪儿拿；模型会背，但不知道怎么落到题目；论文模板有了，但最后还是靠熬夜临时拼。

所以我现在更想把备赛做成一个工程，而不是一个资料包。

math-2026 当前的目标是：

  1. 代码能快速启动：常见预测、优化、评价、仿真模块可以直接改数据运行。
  2. 论文能快速成型：LaTeX / Typst 模板提前跑通，摘要和句式有可复用骨架。
  3. 历年题能快速对照：不是只看 PDF，而是尽量保留完整工程、论文、代码、结果图。
  4. 经验能沉淀下来：读完优秀论文后，把方法写回文档，而不是留在聊天记录里。
  5. 跨设备协作清楚：Windows 主要跑模型，Mac 主要写论文和整理材料。

这个方向有点朴素，但我越来越觉得它重要。比赛现场最怕的不是“完全不会”，而是会一点、资料也有一点，但三个人的工作无法合流。

这些工程最大的价值不是“抄一个模型”，而是看一个完整队伍如何把题目语言翻译成变量、目标函数、约束、算法、图表和论文。

经验文档：把读论文变成可复用方法

目前我最看重的几份文档是：

  • docs/往年优秀工程建模手法分析.md
  • docs/优秀论文排版画图与摘要写作方法.md
  • docs/论文写作模板.md
  • docs/备赛指南.md
  • docs/windows-开发环境.md
  • docs/资源汇总.md

其中前两份是最近投入最多的。

往年优秀工程建模手法分析.md 主要回答：题目要求如何翻译成数学对象。比如 A 题里的几何/物理问题，常常要先变成“路径参数 + 约束方程 + 可行性判定器”；B 题里的实验或工程决策题，常常要把“测量、检测、布设、调度”变成可计算的目标函数；C 题的数据决策题，则更依赖清洗、预测、评价和优化链条。

优秀论文排版画图与摘要写作方法.md 则更关心论文表达。它里面有一个我觉得很重要的判断：优秀论文给人的第一印象，往往不是用了多高级的算法，而是第一页摘要能看出主线，前几页能看出问题拆解，每一问都有“问题分析 -> 模型建立 -> 求解结果 -> 检验或解释”的闭环。

这个闭环是我现在判断论文质量时最在意的东西。

2025 B：国奖和省奖的差距在哪里

最近最有启发的一次对比，是看 2025 B “碳化硅外延层厚度的确定”。

我拉了两份参考：

  • 一份是国奖论文和工程；
  • 一份是省级奖项论文和工程。

同一道题，差距非常直观。

省奖论文并不是不会做。它也写了菲涅尔方程、色散模型、多光束干涉、厚度计算、误差分析，内容很多，页数也更长。但读起来更像“把很多正确模块堆齐”。

国奖论文更强的地方，是它把物理模型、参数反演、算法求解和结果验证连成了一条链：

这里最值得学习的不是“差分进化 + L-BFGS-B”这两个算法名，而是它把算法放在一个明确的反演框架中：参数为什么是这些、目标函数是什么、拟合好不好、误差是否影响结论。

我从这次对比里记下几条赛时原则：

  1. 图表必须进入论证链。核心图不能只是流程图或截图，应该能回答“准不准、稳不稳、哪里不准”。
  2. 每一问都要说明它是否影响下一问。比如多光束干涉不能只判断存在与否，还要说明是否需要修正前面的厚度结果。
  3. 误差分析不能泛泛罗列来源，要说明误差对最终答案的影响幅度。
  4. 页数不是优势，证据密度才是优势。
  5. 附录代码最好能一键复现，而不是零散脚本堆在最后。

这次对比让我更确信：国赛论文拼的不是“我知道多少公式”，而是“我能不能把题目、模型、结果和可信度串起来”。

画图：不要装饰，要证明

我以前会把画图理解成“让论文好看一点”。现在觉得这个理解太轻了。

优秀论文里的图表应该有明确任务：

  • 流程图说明怎么求；
  • 拟合图说明模型准不准；
  • 残差图说明误差在哪里；
  • 灵敏度图说明结论稳不稳；
  • 结构图说明模型如何分层；
  • 对比表说明方案为什么优。

也就是说，图不是装饰，而是证据。

摘要：第一页决定评委是否愿意继续读

摘要现在被我放到非常高的优先级。它不应该只是“本文建立了某某模型，使用某某算法”，而应该在第一页交代：

  1. 题目对象是什么；
  2. 每一问用了什么方法；
  3. 得到了什么关键数字；
  4. 结果如何支撑后续问题；
  5. 模型有什么检验或亮点。

Windows 跑模型，Mac 写论文

我现在的设备分工也更清楚了：

  • Windows：跑 Python、Matlab、Jupyter，生成数据、图表和中间结果；
  • Mac：写 LaTeX / Typst，整理文档，做论文表达；
  • GitHub：作为两端同步的主通道。

这个分工的好处是，计算环境和写作环境互不干扰。Windows 端专注“算得出来”，Mac 端专注“写得清楚”。图表统一从 Windows 生成到项目目录，Mac 只负责引用和排版，减少跨平台依赖差异。

当然，这也要求仓库里的工程必须是普通文件，而不是本地路径或子模块指针。所以最近拉完整外部工程时，我都尽量把嵌套 .git 去掉，让 Windows 端直接 git pull 后就能看到论文、代码、数据和图表。

我希望比赛时遵守的工作流

赛时最理想的节奏大概是这样：

  1. 先读题，拆出每问的输入、输出、约束和评价指标。
  2. 选题后建立一个最小可行模型，不急着堆高级算法。
  3. 每一问尽快形成“模型 -> 代码 -> 图表 -> 文字解释”的小闭环。
  4. 代码手输出可复现结果，图表命名清晰。
  5. 论文手同步写摘要、小标题、符号表和结果解释。
  6. 每隔一段时间做一次证据检查：这个结果是否可信，是否影响下一问。
  7. 最后半天不再大改模型，重点修论文表达、图表、摘要和提交格式。

一句话概括：不要等全部算完才开始写，也不要等论文写完才发现图表无法证明结论。

最后：资料不是目的，方法才是

整理这个仓库最大的收获，是我慢慢意识到：备赛不是无限下载资料，而是建立自己的判断体系。

看到一个工程，要问：

  • 它把题目翻译成了什么数学对象？
  • 它的目标函数和约束是否清楚？
  • 它的图表是否能证明结果？
  • 它的误差分析是否影响最终结论？
  • 它的代码能否复现论文里的数字？

这些问题比“用了什么高级算法”更重要。

接下来我想继续做两件事：一是把 2025 B/C 的成熟工程继续拆成可复用模板；二是把论文图表工具和写作模板打通，尽量让赛时每个结果都能快速变成可放进论文的证据图。

如果这件事能做好，math-2026 就不只是一个备赛文件夹，而是一套真正能在三天比赛里支撑协作的系统。
